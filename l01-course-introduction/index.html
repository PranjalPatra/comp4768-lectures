Native Apps

Native development uses the tools and user-interface components of a particular platform.

PlatformLanguages associated with its development
iOSObjective-C, then Swift
AndroidJava, then Kotlin

Earlier mobile platforms included Symbian, Windows Mobile, and BlackBerry. The arrival of iPhone and Android expanded the mobile application market.

Supporting iOS and Android separately requires maintaining platform-specific code, testing both versions, and working with different development tools.

Cross-Platform Development

Cross-platform development aims to share application code across platforms.

The business reason is straightforward: reach users on more devices without repeating all the development work.

Different approaches share different parts of an application:

  • a runtime can execute shared application code;
  • a web container can display an interface built with web technologies;
  • a framework can use native components or draw its own interface.

Adobe Flash and AIR

Flash and AIR allowed developers to package ActionScript applications for desktop and mobile use. They were suited to multimedia and interactive content.

The approach offered shared code, but mobile applications faced constraints involving the runtime, performance, battery use, and platform support.

Web-Based Mobile Apps

Apache Cordova and PhoneGap used HTML, CSS, and JavaScript inside a mobile application's WebView.

A WebView is a component that displays web content inside an application.

  • Developers could reuse web development skills and share code across platforms.
  • Plugins provided access to device features.
  • The interface and performance depended on the web container and the application.
  • Complex interfaces and hardware access could require additional work.

React Native

React Native combines JavaScript and React with native user-interface components. Facebook introduced it in 2015.

It offers shared application code, a development workflow with rapid feedback, and access to native modules when needed.

The use of native components is an important distinction from a WebView-based interface. Platform-specific behaviour can still require native development knowledge and testing.

Dart

Dart is Google's programming language for client applications. It is the language used to write Flutter applications.

Its features include:

  • classes and interfaces for organizing code;
  • static typing with type inference;
  • null safety for handling values that may be absent;
  • asynchronous programming with async and await;
  • garbage collection for memory management.

Flutter

Flutter is Google's open-source toolkit for building application interfaces from a shared codebase.

A Flutter interface is composed of widgets. Widgets describe elements such as layouts, text, buttons, and forms.

Flutter supports mobile applications as well as web and desktop targets. Its rendering approach gives developers control over the interface across platforms.

Dart is the programming language. Flutter provides the interface framework and development tools.

Rendering and Hot Reload

Flutter draws its widgets through its rendering system, rather than relying on a corresponding native control for every widget.

For mobile development:

  • Just-in-Time (JIT) compilation supports the development workflow.
  • Hot reload applies many code changes while preserving application state.
  • Ahead-of-Time (AOT) compilation produces native code for release builds.

Flutter DevTools and the Flutter Inspector help examine application behaviour and interfaces.

Firebase

Firebase provides managed backend services for web and mobile applications. It lets application developers use backend capabilities without managing the underlying servers themselves.

ServicePurpose
AuthenticationUser sign-up and sign-in
Cloud FirestoreStore and synchronize application data
Cloud StorageStore files such as images
Cloud MessagingDeliver push notifications
Cloud FunctionsRun backend logic

The course focuses on integrating services with the application and controlling access to data.

MVVM Architecture

Model–View–ViewModel (MVVM) separates the interface from application state and behaviour. In this course, repositories and services organize data access.

  • View: displays the interface and forwards user actions.
  • ViewModel: holds screen state and handles application behaviour.
  • Repository: manages application data and provides a consistent access point.
  • Service: communicates with Firebase or another external API.

This separation supports testing and changes to the data source without rewriting the screens.

go_router and Riverpod

go_router organizes navigation. Routes identify screens with addresses such as /tasks/42. Routing includes parameters, links to specific screens, redirects, and error pages.

Riverpod organizes shared state and logic through providers. For example, several screens may need the signed-in user or the same list of tasks.

Providers let interested widgets observe state changes. The course uses Riverpod Notifiers and AsyncNotifiers to implement application behaviour, including ViewModels.

Native Apps

The same application may need similar features on both platforms, but separate implementations can create differences in appearance and behaviour. A feature change can require work in both codebases.

Native development provides access to the platform's own capabilities. The practical question for a team is how much code it can share while providing the experience each platform requires.

Cross-Platform Development

A shared codebase can reduce duplicated work, but it does not remove the need to test on the target platforms. Device features, operating-system behaviour, and user-interface expectations still matter.

The approaches below show different answers to the same problem. Each makes choices about how to display the interface and how to reach device capabilities.

Adobe Flash and AIR

This project is an example of cross-platform development before the tools used in this course. The video demonstrates the application built for that research work.

Flash and AIR belong to the historical context of the course. The course applications use Dart and Flutter.

Web-Based Mobile Apps

This approach places a web interface inside an installed application. The application's appearance does not automatically become the same as the platform's native controls.

Plugins connect the shared application to capabilities provided by the device. That connection is an important part of the approach, because web content alone does not provide every mobile capability.

React Native

React Native is one approach to sharing application code while using platform components for the interface. Flutter takes a different approach to rendering, described below.

Framework choice depends on the team's experience, application requirements, and target platforms. A feature table alone cannot establish that one framework will always be faster, smaller, or easier to maintain.

Dart

Dart began with a focus on web development and became the language used by Flutter. In this course, Dart supplies the language constructs needed to express application behaviour.

Type inference lets Dart determine some types without a written annotation. Asynchronous programming supports work such as waiting for data without treating every operation as an immediate result. These are topics to learn in the Dart foundation, rather than syntax to memorize during this introduction.

Flutter

A widget can describe a visible control or help arrange other widgets. Larger interfaces are built by composing smaller parts.

The course focuses on the concepts needed to build applications, then use documentation and examples to extend them. It does not attempt to cover every widget or platform feature.

Rendering and Hot Reload

The rendering approach supports consistent custom interfaces across platforms. It does not remove the need to check performance and behaviour on the devices an application supports.

Hot reload shortens the cycle between changing code and seeing its effect. Some changes require a restart, so it should not be understood as a promise that every edit can preserve all state. The compilation description here concerns mobile builds.

Firebase

Firebase also includes Realtime Database and Firebase AI Logic, which the introductory deck identifies as services for synchronized data and access to Google's Gemini models. Listing a platform service does not make it a required course topic.

Managed services reduce the infrastructure a developer must operate. Application developers still have to design data access, handle errors, and configure security correctly.

Flutter application architecture guide

go_router and Riverpod

A deep link opens a particular location inside an application. Navigation rules also determine what happens when the user follows a link without being signed in or requests a location that does not exist.

State includes values that the interface depends on, such as a selected task or the result of a data request. Network requests also have loading and error states. Riverpod supports organizing those states, retaining provider results, and substituting implementations for tests.

These tools address different responsibilities: go_router handles where the user is in the application, while Riverpod helps manage the data and behaviour used there.

Dart and Flutter Topics

The Dart topics include var, final, const, and late, lists, sets, maps, conditionals, loops, and switch expressions. Functions include optional and named parameters. Class topics include constructors, getters, setters, abstract classes, privacy, and libraries.

The asynchronous topics include Future, async, await, and streams. Error handling includes try, catch, and finally.

Flutter topics include displaying images and building a stateful application. Tabbed interfaces use TabController, TabBar, and TabBarView.

Application Architecture and Services

The architecture material begins with ChangeNotifier, ListenableBuilder, and a fake in-memory repository. Project folders separate UI, ViewModels, repositories, services, routing, and domain models. The optional use-case layer is outside the course scope.

Navigation includes path and query parameters. State management examines the limits of setState(), then introduces providers, NotifierProvider, list state, immutable updates, derived providers, ref.watch, and ref.read. The ViewModel is also implemented as a Riverpod AsyncNotifier.

Firebase topics include project setup, the FlutterFire CLI, authentication gates, and FirebaseAuthService. A Firebase implementation replaces the fake repository while preserving the View and ViewModel. Firestore topics include reads and writes, filtering, ordering, indexes, data modelling, subcollections, transactions, batch writes, realtime listeners, and offline behaviour. Cloud Storage and image_picker support image uploads.

Security covers authentication, ownership, public and private access, and Firestore and Storage Security Rules. The Firebase Emulator Suite supports local testing of Authentication, Firestore, Storage, and rules. Device topics include camera and image workflows, location, motion sensors, permissions, notifications, and platform constraints.

Agentic development includes coding harnesses, AGENTS.md, reusable skills and workflows, MCP and other integrations, delegation of defined tasks, and testing and review of generated code. MCP connects coding tools with other services and capabilities.
